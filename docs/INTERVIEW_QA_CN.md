# ClinDataForge 技术面试问答（20 题）

> 面向蚂蚁集团 2027 届「医疗大模型数据科学家—平台技术」岗位。所有数字均来自本仓库
> 冻结产物，可在 `reports/` 与 `docs/` 中复核。答案按"做了什么—为什么这样做—代价是什么"组织。

## 一、PHI 脱敏（第二阶段）

**Q1. 你的 PHI 评测集是怎么构建的？凭什么说它是独立的？**

两个来源，都在构建期和审计期各做一次 SHA256 校验：
- 英文部分用 ASQ-PHI v1（MIT 许可，1,051 条第三方合成的临床查询），按 HuggingFace
  revision 固定，与本项目代码无任何共同作者；
- 中文 320 条由本仓库独立模板程序生成，其中 40 条无 PHI 硬负样本各自不同（早期版本
  40 条只差一个数字，被独立审计抓出来后重写）。
划分单位不是单条记录，而是**近重复连通分量**：骨架相同、5-gram Jaccard≥0.50、另一套
掩码下 6-gram Jaccard≥0.50、或同一中文模板族的记录必须落在同一侧。最后用
`scripts/audit_phi_dataset.py` 以另一套掩码独立复核，跨划分泄漏为零。train/dev/test
= 343/396/632 条，冻结测试集在协议冻结后只跑过一次。

**Q2. 四种方法对照的结论是什么？**

冻结测试集（632 条 / 1,942 个金标实体）：
- A 原规则：Recall 0.0803，F1 0.1457——旧资料里"55.56% 召回"是在非独立压力集上
  高估的，独立数据上只有 8%；
- B Presidio + spaCy `en_core_web_lg`：R 0.3084 / F1 0.3446，中文召回仅 0.057，
  且无病历号/医保号识别器（我们刻意不为它自定义规则，保持"开箱基线"口径）；
- C GLiNER `gliner_multi_pii-v1`（ONNX fp16）：R 0.8363 / F1 0.7920；
- D 规则∪GLiNER：**R 0.9042 / P 0.7566 / F1 0.8238**。
配对 cluster bootstrap（2000 次，按语言分层、按近重复分量重采样）：D−A 召回
+0.8239 [+0.8058, +0.8422]，D−C 召回 +0.0680 [+0.0541, +0.0822]，区间均不跨 0。

**Q3. 融合提升 6.8 个召回点的代价是什么？**

三条，全部写进报告：D 仍漏 186 个金标实体（金标字符残留率 5.36%）；**96.55% 的无
PHI 硬负样本被改动**（ASQ-PHI 论文报告的 Comprehend Medical 基线为 86.8–90.0%，同
量级，说明这是该任务形态的固有难点而非我们的实现失误）；规则补充带来了误删——保护
医学字符误删率 14.4%。所以结论只能是"D 适合先脱敏再外发的保守场景"，不能宣称生产
级安全，真实患者入口和正文出口在本仓库里继续关闭。

**Q4. 集成 GLiNER 时踩到的最大的坑是什么？**

`onnx-community` 发布的 int8 动态量化权重在本机表征坍缩：同一探针句子上所有跨度的
最大 sigmoid 概率只有 0.202，prompt 与词表征的余弦相似度全部挤在 −0.06~−0.03——
管线能跑通、不报错、输出形状正确，但**没有判别力**。我们为此写了一个判别力探针
（已知答案的探针句），量化版失败后换 fp16 权重（568MB，SHA256 固定），同一探针
`Anna Smith/NAME 1.000、April 12, 2023/DATE 0.996`。教训写进了 README：**接入任何
第三方模型权重，先跑判别力探针再谈集成**。

**Q5. 阈值是怎么选的？有没有在测试集上调参？**

没有。协议 v2 预注册了"先最大化召回"的选择规则；在 dev 前沿扫描时发现该规则选中
了退化工作点（掩码 22.8% 保护医学字符、改动 100% 硬负样本）。我们在**读取任何
test 数据之前**把协议修订为 v2.1（每方法独立最大化 F1），修订原因和时间写进协议与
报告，dev 全前沿数据保留可查。然后冻结数据/配置/模型/代码 SHA256，test 只跑一次。

**Q6. spaCy 环境问题怎么解决的？**

spaCy 3.8.x 搭配 preshed≥3.0.10 / cymem≥2.0.9 时，加载 `en_core_web_lg` 管线抛
`OverflowError: Python int too large to convert to C ssize_t`（Cython 层哈希表宽度
问题）。定位到依赖组合后锁定 `preshed==3.0.9 / cymem==2.0.8 / murmurhash==1.0.10`，
写进 `requirements-phi.txt`，并在隔离环境 `.venv-phi`（Python 3.10）中运行，不污染
主环境。

## 二、知识约束合成（P0，第三阶段）

**Q7. 为什么不用大模型直接生成合成病历？**

三个原因：一是本任务要求**可追溯的事实约束**——LLM 自由生成无法保证"该病不该出现
的表型不出现"，而自评不能代替独立金标准；二是合规——不允许把任务外包给无授权的
收费 API；三是可复现——我们的生成器是纯标准库、固定种子、逐字符跨度自洽，验证器可
以独立重放。LLM 在本项目中的合理位置是"候选改写器+人工审核队列"，而不是事实来源。

**Q8. 知识来源是什么？许可核实过吗？**

Human Phenotype Ontology：`hp.obo`（release 2026-09-01）与 `phenotype.hpoa`
（2026-09-02 版疾病-表型注释），SHA256 均记录在 `data/external/hpo/`。许可条款逐条
核实过：允许自由使用，要求署名与展示版本号，不得改动本体内容再分发——本项目原样
使用并完整署名，合规。快照含 20,482 个表型术语、12,867 个疾病注释。我们没有用
需要申请的 MIMIC/i2b2 数据。

**Q9. 合成一条病历的具体流程？**

以病例为单位：先按 HPO 起病注释（如"儿童期起病"）采样年龄（Turner 综合征固定女性、
Lowe 综合征固定男性这类已知性别约束硬编码为知识规则）；再从该病的 HPOA 注释集中
**按注释频率加权采样**表型（TAS/PCS 证据代码与 PMID/ORPHA 引用随实体一起保留）；
按 3 个模板族（门诊/入院/病程记录）× 3 复杂度渲染中英文文本；状态分 确认/疑似/
既往/否认 四类，否认表型只能取自该病注释集或人工白名单，保证"否认的内容医学上
也合理"；检验值只对 4 个有文献依据的检验关联表型生成（如 Lowe 综合征→ALT/AST
升高），方向与参考区间一致，数值按显示单位反算标准值并携带换算因子。

**Q10. 怎么验证合成质量？怎么防止生成器和验证器"串通"？**

`scripts/validate_synth.py` 是**独立验证器**：只读产物 JSONL 和 HPO 快照，不 import
生成器代码。检查项：实体跨度与文本逐字符一致（span integrity）、每个表型实体必须
属于该病注释集（知识约束违反）、检验值方向与参考区间一致且单位换算正确、疾病/表型
覆盖、骨架 5-gram 近重复率、模板与词汇多样性。实测：2,400 病例，知识约束违反
**0/2400**，检验错误 0，跨度错误 0，同疾病内近重复对（Jaccard≥0.7）占 0.18%。
"串通"风险真实存在过——g/dL→g/L 换算方向两边曾同错互相掩盖，是单元测试抓出来的，
之后验证器改用独立换算路径。

**Q11. 生成的数据能不能直接拿去 SFT？**

不能，我们刻意这么设计。输出带 `PENDING_HUMAN_REVIEW` 队列（199 条边界样本），
结构化 JSONL 中每个实体保留 HP 编码、证据代码、引用、规则版本、随机种子，满足
血缘要求；但报告明确写了：知识一致 ≠ 医学正确，无 PHI 金标 ≠ 无隐私风险，合成数据
的训练价值必须用下游实验验证，不能自封。

## 三、结构化与质量流水线（P1）

**Q12. 流水线整体架构？**

九段：Schema 校验 → HPO 词典表型抽取（含同义词、最长匹配优先、英文词边界）→
上下文判定（确认/疑似/既往/否认，分句窗口 + 接续分句回溯）→ 检验解析与单位标准化
v2（ALT/AST/血糖/血红蛋白，携带换算因子与冲突标记）→ PHI 安全门控（复用第二阶段
D 方法：规则∪GLiNER fp16）→ 近重复检测（患者组+就诊组约束，不同患者/不同就诊不
误并）→ 知识一致性检查（抽取的表型是否属于该疾病注释集）→ 质量评分与异常隔离 →
复核队列/结构化输出。每段记录耗时与版本号进 lineage，SQLite 落审计。

**Q13. 上下文判定怎么做的？为什么不用 medSpaCy 的 ConText？**

medSpaCy 的 ConText 是英文规则集，对中文"否认/未见/不伴/既往"无能为力，且引入
完整 medSpaCy 会带入大量我们用不到的依赖。我们实现了一个 60 行的分句窗口分类器：
cue 词表分语言，窗口到分句符为止（中文分句符含逗号，英文不含——因为英文否定列举
用逗号分隔，"denies A, B"中 B 也在否定范围内，这个差异是实测错误分析发现的）；
另有接续分句回溯："既往有 A，并有 B"中 B 继承既往状态。指标按"匹配上的实体的状态
判定准确率"报告，混淆矩阵留档。

**Q14. 近重复检测怎么避免误并同一患者的不同就诊？**

评测对设计了四类（每类 40 对）：同一就诊的重复副本（DUPLICATE）、同患者不同就诊
（NOT_DUPLICATE）、同疾病不同患者（NOT_DUPLICATE）、同就诊但检验值更新
（NOT_DUPLICATE）。判定同时使用患者组、就诊组与临床字段冲突保护，逐类报告正确率。
最终结果：160 对全部判对（P/R/F1 均 1.0）。过程中还发现并修复了一个评测忠实度问
题：最初评测用原始文本跑，出现 4 个 FN——但生产流水线是在**脱敏后**的文本上去重
的，换成与生产一致的规则掩码口径后这 4 个"漏检"消失。教训：评测 harness 必须复现
生产的数据流形态，否则测的是一个不存在的服务。

**Q15. 流水线里的"质量评分"和"隔离"具体指什么？**

每条记录产出固定问题码（如 SCHEMA_INVALID、LAB_CONFLICT、KNOWLEDGE_VIOLATION、
POSSIBLE_DUPLICATE、PHI_RESIDUAL_RISK），命中隔离规则的进 `quarantine.jsonl` 并
保留原因码与血缘，接受的进 `structured.jsonl`。两路输出都不含未脱敏正文——文本出口
仍然关闭，导出的结构化字段是实体级投影。

数字分两版，因为上下文修复前后差异很大：
第三阶段（`pipeline-med-1.0.1`，固定窗口）2,400 进 / **2,332 接受 / 68 隔离**；
第四阶段（`pipeline-med-1.1.0`，作用域判定）2,400 进 / **2,355 接受 / 45 隔离**。
差的 23 条原来因 `KNOWLEDGE_INCONSISTENT_PHENOTYPE` 被隔离，而隔离的直接原因是
上下文判错——判对之后自然通过，不是我放松了阈值。剩下 45 条是生成器自身的检验值
冲突（血糖 29 + ALT 16），属于真实坏数据，继续隔离。

## 四、评测方法与工程（P2/P4）

**Q16. 模板内自检和独立测试为什么必须分开报告？**

因为合成数据的金标来自生成器自己，流水线抽取器用的又是同一套 HPO 词典——在合成
集上表型抽取 P/R 接近 1.0 是"自己考自己"，只能证明流水线与生成器语义一致，不能
证明对真实文本有效。我们的报告里明确标注"模板内自检"口径，独立效力仍以第二阶段
的 ASQ-PHI 独立评测为准。把两者混报是这个领域最常见的自我夸大手法。

**Q17. 数据血缘怎么做的？**

三级：语料级——每个外部资源记录下载地址、版本、SHA256、许可结论
（`SOURCE_MANIFEST.json`）；记录级——每条合成病历携带疾病 ID、HP 编码、证据代码、
引用、规则版本、种子；运行级——每次流水线运行有 provenance（输入清单哈希、配置
哈希、代码版本），SQLite 审计库存伪名索引与计数，不落正文。

**Q18. 如果让你把这个系统推向真实医院数据，下一步是什么？**

四道门按顺序过：一、用获得授权的真实去标识化语料（如 n2c2/i2b2 挑战数据，需
DUA）重建独立评测集，现在的 ASQ-PHI 只是合成代理；二、PHI 召回必须到可论证的
水平（当前 0.9042 不够，漏的 186 个实体里 DATE/ADDRESS 长尾需要针对性模型或规则）；
三、过机构 IRB/合规审查与等保/个保法评估；四、灰度+人工复核闭环。在任何一道门
通过之前，正文出口保持关闭——这条写在代码里，不是写在 PPT 里。

**Q19. 这个项目里你推翻过自己什么结论？**

三次。一、旧压力集"召回 55.56%"——独立评测后证实原规则真实召回 8.03%，旧数字是
非独立数据的高估；二、协议 v2 的"召回优先"选择规则——dev 前沿证明它会选中退化
工作点，读取 test 前修订为 F1 最大化并显式记录；三、GLiNER int8 权重——形状正确
但判别力坍缩，如果当时只看"跑通了"就会把垃圾结果写进报告。三次都是靠独立审计/
探针/预注册纪律发现的，这是这个项目真正想展示的方法论。

**Q20. 为什么不能宣称"影像-报告对齐"或"SFT 完成"？**

因为没有真实配对证据和真实训练日志。P3 多模态只被列为未来扩展；SFT 我们只做了
候选数据导出格式（指令/偏好 JSONL schema + 质量筛选规则 + 血缘字段），没有模型
调用授权就没有训练。项目红线是：**所有指标必须来自实际运行**，估算和规划不许写进
结果区。MedMCQA 评测接口（离线解析/打分）已实现，但无 API 授权时只标 BLOCKED，
不编造数字。

## 五、第四阶段：上下文修复与吞吐优化

**Q21. `history` 被判成 `affirmed`，根因到底是什么？**

不是词表不够，是作用域算错。中文既往史写成 `既往史：有A，并有B`，而判定器把 `：` 当断句符，
窗口从冒号之后才开始，`既往史` 落在窗外；后续项 `，并有B` 依赖"接续分句回溯"，而回溯只走
一句就 `break`。所以 783 例全部是中文、全部集中在带段头的模板族，英文因为把 `a history of`
每项重复一遍反而全对。另外还有第二个独立问题：中文表型名自己含否定字（`前脑无裂畸形`、
`无言语`），裸字符 `无` 会从实体名内部误触发否定。

**Q22. 你怎么证明这不是"在测试集上调参"？**

三条纪律。一、把已用于诊断的 2,400 条明确降级为开发集，本轮起不再当测试集。
二、在评测任何新版本之前，用不同 seed、不同句式、不同抽样生成 260 条新语料并记 SHA256 冻结，
之后不允许改。三、把线索词表拆成两套——只换作用域（v1 词表）和换作用域+词表——分开报告，
这样"改进来自机制还是来自多认几个词"是可分辨的。留出集上作用域单独贡献 221→57，
词表再贡献 57→0。

**Q23. 那 100% 的 history 召回能写进简历吗？**

不能，只能写"留出合成语料上 history 误判 221→0"。原因有三：金标来自同一套模板发射器而不是
临床医生；疾病集合和线索词表与开发集重叠；中文词表只有 214 个表型，真实病历的表述空间远大于此。
这份语料的效力只到"作用域机制在模板结构上是对的"，再往前一步就是临床宣称，我们没有证据。

**Q24. PHI 推理为什么慢？加线程为什么没用？**

ONNX Runtime profiler 显示 MatMul 占 49.4%、**Cast 占 24.5%**。模型是 fp16，而本机 CPU 没有
AVX512-FP16，运行时只能在每个 fp16 算子前后插 Cast 做软件模拟，MatMul 也退化到慢路径（约
1.8 GFLOPS）。Cast 是纯开销，加线程只会让更多线程一起做无用的类型转换：2→4→8 线程实测
2778 → 3099 → 4969 ms/条，越加越慢。换官方 fp32 权重后同一条降到 995 ms，2.79 倍，
Cast 消失、MatMul 走 MLAS。代价是内存 1.35 GB → 2.13 GB。

**Q25. 你不是实现了批处理吗？为什么最后没用？**

实现了，也测了，是负结果。batch 8 反而 1785 ms/条（比逐条 995 慢 1.8 倍），因为批内长度补齐到
最长 chunk，编码器又是算力受限，padding 浪费的算力超过省下的调用开销。按长度排序能把
padding 压下去（1785 → 1248 ms/条，p95 还从 1748 降到 1421），但仍然不如逐条。
这条结论写进了配置文件的 `why_not_batching` 字段，避免下一个人再试一遍同样的东西。

**Q26. 性能优化会不会悄悄改变脱敏结果？你怎么证明？**

两层证明，而且第二层把第一层的结论推翻了——这一点我一般会主动讲。
第一层：五个配置在同样 60 条上逐条比跨度集合，`doc_identity_rate` 全为 1.0000，
缺失和新增跨度都是 0。这时候很容易收工写"输出完全一致"。
第二层：在**原冻结测试集**（632 条，先校验数据 SHA256 与第三阶段一致）上重算 P/R/F1，
和冻结结果并排打印。结果是 C 一致率 0.9968、D 一致率 0.9984，共 3 个跨度差异：
ZH-0140 的手机号是正确找回（C 的 TP +1），EN-0554 把 `50-year-old male` 判成姓名是新增误报。
关键性质是**缺失跨度为 0**——优化后的数值差异从未让原有检测消失；
D 的召回 0.9042、TP 1756、FN 186 一个都没变，只有 precision 从 0.7566 掉到 0.7562。
看到这 3 个差异我**没有**回去调阈值 0.2，因为在测试集上看到差异再调参就是把测试集变成开发集；
差异和"没调参"的决定都写进了配置文件的 `frozen_test_regression` 字段。

**Q27. 这轮你发现的最难看的问题是什么？**

三个。一、程序化偏好数据里，`hallucinate_phenotype` 规则硬编码了"发热 HP:0001945"，
而有 22 条记录的疾病本来就注释了发热——这些"错误答案"其实是对的，2,332 对里有 0.94%
标签噪声；另有 113 条追加的表型本来就在正确输出里，变成重复项而不是幻觉。
改成从未注释的表型里采样后，两类都是 0。
二、验证器 import 了生成器用的同一张参考区间表，常数级循环验证还在：如果区间表本身
错了，生成器和验证器会一起错、一起通过。真正的独立检查只有跨度完整性、HP 编码存在性
和第三方换算常数复算。
三、我自己的审计脚本也有过一次假检查：规则改成按病例采样后，审计还在用常数
"发热是否在注释集里"来判断，结果报出 29 这种没意义的数字。后来改成取 `rejected`
里被追加的最后一个 `hp_id` 去比对病例金标，并用**修复前的导出**复算验证它能精确
复现原来的 22 例——检查本身也要被检查，不然它会从"抓错"退化成"报数"。

**Q28. 你的合成数据现在可以拿去训练了吗？哪些能用、哪些不能？**

分用途回答，不给一个笼统的"能"。可以作训练候选的：状态标签监督（修复后与金标不一致
0 / 21,640）、表型抽取监督（模板内 F1 0.991）、检验标准化监督（1,277 / 1,277）、
Schema 格式遵从（100% 可解析）。不能的：任何泛化结论（test 与 train 的
(模板族, 复杂度, 疾病) 三元组碰撞 64.39%，16 种疾病在三对划分里全部重叠）、
中文鲁棒性（中文术语表只有 214 条，测试集和训练集用的是同一份，属于自证）、
偏好对的偏好质量（程序化腐化，不是人类标注）、医学正确性（存在常数级循环验证）、
临床可用与隐私安全（无真实数据、无合规认证）。

**Q29. 为什么说你的 test 划分不能当泛化基准？**

因为我的划分是按患者组哈希做的：跨划分没有相同患者、没有重复文本、没有近重复对，
这三点都过了。但模板族有 5 种、复杂度 3 种、疾病 16 种，三元组空间只有 240 个格子，
2,355 条样本必然大量落进同一格——实测 test 记录里 99.02% 的三元组在 train 出现过
（换一个方向，train 里有 64.39% 的记录落在与 test 共享的三元组里，两个分母不同）。
更糟的是疾病名直接写在正文里（train 100%，脱敏后仍有 85.37%），
同格子样本等于把答案也给了。模型可以靠"这个格子常见哪些表型 + 正文里那个病名"抄答案，
不需要真的学会抽取。
要真正可声称泛化，得按疾病做留一划分，那样 test 每折只有约 147 条，统计功效不足，
会得到"看起来显著其实是噪声"的结论。所以我宁可写清楚它只能做联调集。

**Q30. 端到端提速多少？为什么比微基准低？**

整条九段流水线跑 2,400 条：79.1 分钟 → 42.0 分钟，1.89×；微基准是 2.78 倍。
差在两处，都能解释。一、流水线把门控做成 2 条一批的预跑批次（`batch_size=1` 时
实际 2 条一批），批内 padding 浪费约 4.6%，而微基准是严格逐条。二、抽取+上下文
从 5.6 ms/条涨到 8.2 ms/条，因为作用域判定要预计算终止符表、扫触发词、做掩码，
比固定窗口贵。8.2 ms 相对 1,040 ms 的门控可以忽略，所以整体仍是净加速。
我没有为了好看把这两个数字混着用。

**Q31. 你发现疾病来源清单和实际生成数据对不上，是怎么查的、怎么处理的？**

先做集合比对：`disease_selection.json` 里的 16 个 ID 与生成器实际用的
`CURATED_DISEASES` 只有 3 个重合（ORPHA:506、OMIM:276700、OMIM:117550）。
然后用当前 `select_rare_diseases()` 以文件里记录的 seed=20261026、min_phenotypes=8
重算一遍，**精确复现了旧文件的 16 个 ID**——说明它不是损坏，而是早期算法选择器的真实产物。
根因是后来生成器改用了人工核验的 16 病清单，而 `build_hpo_kb.py` 设计为拒绝覆盖已存在的
选择文件，旧文件就一直留在原处，文档还指着它。
处理方式是不改历史：新增 `lineage-1.0.0` 清单，逐条核验 2,400/2,400 条记录、
22,156/22,156 个表型实体都能回到实际使用疾病的 HPO 注释集，记录级溯源与快照一致 2,400/2,400，
所有输入文件带 SHA256；旧文件登记为 `superseded_artifact`，不删除、不覆盖。
这件事的教训是：write-once 保护了历史，但必须另有一个"as-run"指针，否则历史会变成误导。

**Q32. 260 条留出语料只有 64 个近重复簇，这是否推翻你的结论？**

不推翻点估计，但推翻"260 个独立样本"这个说法。实测 260 条只有 186 种不同规范化文本，
Jaccard≥0.8 有 706 对，连通分量 64 个，最大簇 10 条，没有单例。原因是模板发射器 +
每种疾病的核心表型集很小，重复抽样会撞出相同文本。
所以我把推断单位从"提及"改成"簇"，做 2,000 次 cluster bootstrap：
v1 准确率 95% CI [0.6337, 0.7734]，v2 [0.9451, 1.0000]，宏 F1 [0.9232, 1.0000]。
区间仍然分离，结论方向不变，但区间比按提及算宽得多。
另外它和开发集共享生成代码、16 种疾病、中文词表，所以只能叫"同生成器留出合成语料"。
如果簇级配对检验显示差异不显著，我会撤回结论；现在不是这种情况。

**Q33. 生成器和验证器共享检验常数表，你怎么证明循环验证是真实存在的？**

先做静态检查：两边都 `from clinforge.hpo_knowledge import REFERENCE_INTERVALS`，
验证器用同一组因子和同一组区间重算，所以表错了两边一起错。
然后建第二条路径 `clinforge/lab_standards.py`：换算因子由分子式和 CIAAW 原子量推导
（葡萄糖 180.156 g/mol、肌酐 113.120 g/mol），g/dL→g/L 用 SI 词头定义，ALT/AST 是 U/L
不做质量换算；这个模块不 import 共享表。用它复算 1,277 个检验值，0 个换算错、0 个方向错。
最后做注入实验：在内存里把共享表改成错误因子（葡萄糖 20.0、HGB 12.0）和错误区间
（血糖上限 4.5、HGB 下限 160），生成 300 条病例。共享表路径 0 错 0 错——按构造必然通过；
独立路径检出 26 个换算错、10 个方向错。实验后表已恢复，金标一个都没改。
边界也要说清楚：这只证明"实现没有把常数写错"，不证明演示区间在临床上正确；
真实参考区间取决于方法、分析仪和人群，本机没有实验室标准或室间质评数据。

**Q34. 这一轮你主动公开了哪些对项目不利的发现？**

六个。一、疾病清单 3/16 不一致，旧文件还被文档指着。二、test 记录 99.02% 的三元组
在 train 出现过，疾病名 100% 出现在正文（脱敏后 85.37%），金标还含 `disease_suspected`。
三、260 条留出语料只有 64 个近重复簇。四、生成器与验证器共享常数表，循环验证真实存在。
五、PHI 优化后冻结集有 3 个新增跨度，D 的 precision 从 0.7566 掉到 0.7562。
六、中文术语是单人机助翻译，没有专家审核；96.55% 的无 PHI 硬负样本被改动。
这些都不是"补个说明"就过去了——每一条都改了代码或改了口径：新增血缘清单、把留出集
降级为同生成器验证、建独立常数路径、保留 3 个跨度差异不回改阈值、把翻译状态写进审计。
