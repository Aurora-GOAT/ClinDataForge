## 0. 审计方法与效力声明

审计不读任何「自检报告」，只读四类原始产物并重新计算：

| 输入 | 路径 | 用途 |
| --- | --- | --- |
| 生成语料 | `data/phase3_synth/gen/notes.jsonl` | 溯源、循环验证、翻译、偏好标签的真值来源 |
| 知识库快照 | `data/phase3_synth/kb/hpo_snapshot.json` | 疾病-表型注释集、HPO 术语集 |
| 流水线输出 | `data/phase4_synth_v2/pipeline_out/` | 上下文标签污染比对 |
| 训练候选导出 | `data/phase4_synth_v2/training_candidates/` | 分割泄漏、偏好对、状态标签比对 |

**审计本身的局限（先说清楚）**：

1. 审计脚本与生成器同一个人写。它能发现**实现错误**（偏移、换算、标签复制），
   但无法发现**共同误解**（例如我和生成器都认为某个表型属于某疾病）。
2. 「知识约束违反 = 0」这个数字，本质上是在检验生成器有没有遵守自己的采样契约，
   **不是医学正确性证明**。详见第 2 节。
3. 所有病例都是程序化合成文本，没有一份真实病历进入过本项目。

## 2. 生成器与验证器是否循环验证：部分是，已披露

这是本轮审计里**最难看的一条**，也是最有价值的一条。

### 2.1 结论

| 检查类型 | 是否独立 | 说明 |
| --- | --- | --- |
| 跨度完整性（实体文本 vs 偏移） | **独立** | 与生成逻辑无共享状态 |
| `hp_id` 是否存在于 HPO 快照 | **独立** | 对照外部本体文件 |
| 单位换算算术 | **独立**（算术独立，常数共享） | 验证器重新推导 `180.16/10` 与 `10.0`，不 import 生成器的换算函数 |
| 近重复统计 | **独立** | 只读生成的文本 |
| 「表型属于该病」 | **构造性循环** | 生成器从注释集采样，验证器检查是否在注释集内 |
| 检验方向与参考区间 | **构造性循环** | 方向与区间来自同一张表，表错了两边一起错 |

### 2.2 具体证据

验证器 `scripts/validate_synth.py` import 了项目内的三个常量：

```
REFERENCE_INTERVALS, GENERIC_NEGATABLE_ZH, GENERIC_NEGATABLE_EN   （来自 clinforge/hpo_knowledge.py）
```

它**没有** import 生成器的内部标记（`validator_imports_generator_markup = false`），
所以「验证器读取金标再做检查」这种最严重的作弊不存在。但参考区间表是共享的：
如果那张表里血糖的参考下限写错了，生成器会照着错的写，验证器会照着错的判，两边都通过。

换算常数我用独立字面量重算了一遍做交叉验证：

| 分析物 | 项目内常数 | 独立字面量 | 是否一致 |
| --- | --- | --- | --- |
| 血糖 mmol/L → mg/dL | 18.016 | 180.16 / 10 | 一致 |
| 血红蛋白 g/dL → g/L | 10.0 | 10.0 | 一致 |

### 2.3 这个缺陷不是假设，它已经发生过一次

第三阶段测试抓出的 `g/dL → g/L` **换算方向错误**，正是因为生成器和验证器共用同一条错误路径，
两边互相印证、全部通过，直到人为把两条路径分开才暴露。这就是循环验证的真实代价：
**它不会让错误变多，它会让错误隐身。**

### 2.4 本轮做了什么、没做什么

- 做了：把循环验证的边界写成机器可读字段（`checks_that_are_independent` /
  `checks_that_are_tautological_by_construction` / `known_shared_failure_mode`），
  并且不再把「知识违反 0/2400」当作独立验证成果宣传。
- 没做：彻底消除常数共享需要引入外部参考区间标准（如机构检验手册），
  本项目没有授权数据，**保持 BLOCKED**。

## 3. SFT 分割（1921 / 230 / 204）是否存在泄漏

修复后导出共 **2,355** 条接受样本，按患者组哈希分成 train 1,921 / dev 230 / test 204。

| 检查项 | 结果 | 判定 |
| --- | --- | --- |
| 跨划分完全相同的文本 | **0** | 通过 |
| 跨划分共享患者组 | **0** | 通过（按 `patient_group` 哈希分桶） |
| 跨划分近重复对（Jaccard ≥ 0.8，脱敏文本口径） | **0** | 通过 |
| 跨划分模板骨架碰撞 | **0** | 通过 |
| 跨划分疾病重叠 | **16 / 16**（三对划分都是全部重叠） | **不通过** |
| test 与 train 共享（模板族, 复杂度, 疾病）三元组的 train 侧记录比例 | **64.39%**（1,237 / 1,921） | **不通过** |
| test 记录中三元组已在 train 出现的比例（另一方向） | **99.02%**（202 / 204） | **不通过** |
| dev 与 train 同一比例（train 侧） | 65.80% | **不通过** |
| 答案泄漏（疾病名直接写在正文里） | 是（train 100%，脱敏后 85.37%） | 见下 |

### 3.1 为什么骨架不撞、三元组却大量复用

模板族只有 5 种（门诊 / 住院 / 转诊 / 门诊短病历 / 会诊），复杂度 3 种，疾病 16 种 →
三元组空间只有 240 个格子，而样本有 2,355 条。**这是设计决定的，不是 bug**：
我刻意让每种疾病都覆盖多种模板族。

两个百分比分母不同，不矛盾：64.39% 是"train 记录中落在与 test 共享的三元组里"的比例；
99.02% 是"test 记录中三元组已在 train 出现过"的比例。后者更直观，也是更该警惕的口径。

后果很具体：模型看到 `(outpatient, standard, MELAS)` 的训练样本后，再遇到同格子的测试样本，
它可以从「疾病名出现在正文里 + 这个格子的常见表型组合」直接抄答案，**不需要真的学会抽取**。

### 3.2 判定

> **这组分割不能作为泛化基准（generalisation benchmark）。**
> 它可以作为**格式遵从 / Schema 合规 / 流水线联调**的训练集与验证集，
> 但不能用它的 test 分数去声称「模型学会了在未见疾病/未见模板上抽取」。

要得到可声称泛化的分割，需要按**疾病**做留一划分（16 折，每折留 1 种疾病），
或引入新的模板族。本轮不做——因为一旦按疾病划分，test 集就只有 1/16 的数据，
在 2,355 条规模下统计功效不足，会得到「看起来显著其实噪声」的结论。

### 3.3 260 条上下文留出语料也有重复结构

对上下文留出集单独做近重复审计（`scripts/audit_split_relations.py`），结果是：

| 指标 | 数值 |
| --- | --- |
| 记录数 | 260 |
| 不同规范化文本 | **186** |
| 内部近重复对（Jaccard ≥ 0.80） | **706** |
| 连通分量（簇） | **64**，最大簇 10 条，无单例 |
| 与 train/dev/test 的患者/精确文本/骨架/近重复 | 全部 0 |

也就是说，1,618 个提及不是 1,618 个独立观测。按 64 个簇做 cluster bootstrap 后，
v2 准确率 95% CI 为 [0.9451, 1.0000]，v1 为 [0.6337, 0.7734]（`holdout_bootstrap.json`）。
结论仍然成立，但**"260 条独立样本"的说法不成立**，对外只能写"同生成器留出合成语料"。

## 4. 中文翻译核对状态：不是专家金标准

| 项 | 数值 |
| --- | --- |
| 中文表型术语 | 214 |
| 中文疾病名 | 16 |
| 同一中文表面串映射到不同 HP 编码 | **0**（无冲突） |
| 互为子串的术语对（可能导致最长匹配歧义） | 10 |
| 含拉丁字母未翻译的术语 | **0** |

**审核状态：单人、机器辅助翻译 + 抽查。没有临床医生或职业译者审核。**

允许的表述：

- ✅ 「作者整理的中文术语表（curated Chinese gloss）」
- ✅ 「作者翻译的术语」

禁止的表述：

- ❌ 「临床专家金标准」
- ❌ 「经临床医生验证的术语」
- ❌ 「专家审核过的翻译」

残余风险：HPO 官方**没有**中文发布版，中文同义词覆盖只有这 214 个表面串。
因此「模型在未见中文表述上的召回」在本项目内**无法测量**——测试集和训练集用的是同一份术语表，
任何中文召回数字都只反映这 214 个串的覆盖，不反映真实中文病历的表达多样性。

## 5. 程序化偏好数据的可靠性

偏好对共 2,355 条，四类腐化规则：

| 规则 | 条数 | 语义 |
| --- | --- | --- |
| `hallucinate_phenotype` | 967 | 在正确输出后面追加一个该病**不该有**的表型 |
| `flip_status` | 574 | 翻转某个表型的状态（如 affirmed → negated） |
| `drop_phenotype` | 574 | 删掉一个表型 |
| `wrong_lab` | 240 | 把检验值乘 2.5 |

### 5.1 发现的真实缺陷（已修复）

初版 `hallucinate_phenotype` **硬编码**了 `HP:0001945`（Fever）。而 Fever 对其中 **22 条**
病例来说本来就是金标表型——这些「错误答案」其实是对的。另外 **113 条**里 Fever 已经在正确输出中，
追加后变成重复项而非幻觉。

修复方式（`sft-export-2.0.0`）：幻觉得表型改为从 `HPO 全部术语 − 该病注释集 − 当前已输出表型`
中采样，从构造上排除这两种情况。

### 5.2 检查本身也重写了

原审计用「Fever 是否在注释集里」这个常数来判断，规则一改这个检查就失效（会给出 29 这种无意义数字）。
新检查改为：取出 `rejected` 里被追加的**最后一个** `hp_id`，比对**该病例自身的金标注释集**。

用修复前的导出跑新检查，精确复现出 **22** 例；用修复后的导出跑，得到 **0** 例。
这说明检查不是变宽松了，而是变对了。

> 目录里有两个修复前产物，注意区分：
> `audit_prerefix.json` 是**第一次**审计（用的是旧的常数检查，`preference_labels` 里的
> `hallucinated_phenotype_was_actually_annotated = 22` 是它算出来的，但那次数字与检查逻辑
> 恰好都不再适用于新规则）；`audit_prerefix_recheck.json` 是**用新检查重算同两份旧产物**得到的，
> 用来证明新检查仍能抓到老缺陷。看结论请以后者与 `audit.json` 为准，前者只作为过程留痕不覆盖。

| 指标 | 修复前导出 | 修复后导出 |
| --- | --- | --- |
| 偏好对总数 | 2,332 | 2,355 |
| `rejected == chosen` | 0 | 0 |
| 「错答」其实正确 | **22**（0.94%） | **0** |
| 幻觉表型与已有表型重复 | **113** | **0** |

### 5.3 仍然不能声称什么

- 这不是人类偏好标注。`label_status = programmatic corruption, NOT human preference annotation`。
- 可用于：DPO/RLHF **流程连通性测试**、格式监督实验。
- 不可用于：任何关于人类偏好质量、奖励模型准确率的结论。

## 6. 上下文标签污染与训练闸门

任务里明确要求：**修复 history 误判之前，不得把含错误上下文标签的 SFT 候选用于训练。**

### 6.1 闸门指标

把导出候选里的每个表型状态与该病例的金标状态逐条比对：

| 口径 | 匹配提及数 | 状态不一致 | 不一致率 | 主要转移 |
| --- | --- | --- | --- | --- |
| 修复前（`pipeline-med-1.0.1` / 固定窗口） | 21,353 | **823** | **3.85%** | history→affirmed 762、affirmed→negated 30、history→negated 17、negated→affirmed 14 |
| 修复后（`pipeline-med-1.1.0` / `ctxscope-1.1.0`） | 21,640 | **0** | **0.00%** | — |

### 6.2 修复带来的连带效应（可推演，不是巧合）

| 指标 | 修复前 | 修复后 | 说明 |
| --- | --- | --- | --- |
| 输入病例 | 2,400 | 2,400 | 同一份语料 |
| 接受 | 2,332 | **2,355** | +23 |
| 隔离 | 68 | **45** | −23 |
| 隔离原因 `KNOWLEDGE_INCONSISTENT_PHENOTYPE` | 23 | **0** | 上下文错判导致的假不一致 |
| 隔离原因 `CONFLICTING_VALUES_GLUCOSE` | 29 | 29 | 生成器自身的检验值冲突，与上下文无关 |
| 隔离原因 `CONFLICTING_VALUES_ALT` | 16 | 16 | 同上 |

那 23 条被隔离的病例，是因为状态判错后被一致性检查判成「与知识库不一致」。
上下文修好后它们自动恢复正常，**不是我把阈值调松了**。剩下 45 条隔离是生成器本身的检验值冲突，
属于真实的坏数据，应当继续隔离。

### 6.3 闸门裁定

> **闸门从「拦截」变为「放行」，但放行是有条件的。**

可以放行的：

1. 状态标签——修复后 0/21,640 不一致，可作为上下文抽取的监督信号。
2. 表型抽取——F1 0.991（模板内自检口径）。
3. 检验标准化——1,277/1,277（模板内自检口径）。
4. Schema / 格式遵从——100% 结构化输出可解析。

**仍需人工复核或不可用**：

1. 中文术语（214 条）——需临床或专业译者复核，现为作者翻译。
2. 参考区间与检验方向——需机构标准，现为演示值。
3. 任何「泛化能力」结论——三元组复用 64.39%（train 侧）/ 99.02%（test 侧），不能支撑。
4. 偏好对的**偏好质量**——程序化腐化，只能测流程。
5. 真实临床有效性——**未验证，且无数据可验证**。

## 8. 未解决的科学与工程问题

1. **常数级循环验证无法在本项目内消除**——需要外部参考区间标准或第三方标注，均无授权。
2. **分割设计要真正可用，需要按疾病留一划分**，但 2,355 条规模下每折仅约 147 条，统计功效不足；
   要么扩大语料到 2 万条以上，要么接受「只能做联调集」的定位。

4. **`disease_selection.json` 与实际使用的 `CURATED_DISEASES` 不是同一组**，
   命名误导，历史产物不改写，只在文档标注。
